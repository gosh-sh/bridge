Q1. Circuit 1B и Circuit 3 — где зелёные коммиты?

Нужны SHA в двух репах, на которых MockProver (и желательно лёгкий
real-prover sanity-тест) проходят чисто для:
  — fallback attestation (Circuit 1B);
  — BK-set rotation (Circuit 3).

Без этого мы не можем начать Phase 1.C (включение Circuit 3 в
verifyBlock + соответствующий gnark-wrapper и Solidity-верифаер с
опциональным аргументом bkSetUpdateProof). Phase 5.2 первый cut можно
делать только по Primary attestation (Circuit 1a) — тогда 1B не нужен
прямо сейчас, но потребуется до закрытия полного покрытия.


Q2. transition_hashes — мигрировали в ноде или нет?

Поле BlockKeeperSetChangeProofData.transition_hashes должно быть в
новом минимальном Poseidon-формате (см. §8
ENVELOPE_HASH_MERKLE_SPEC.md). Вопрос:

  — миграция уже в ноде (если да, на какой ветке/SHA)?
  — или это работа relayer'а, т.е. мы пересчитываем сами на лету
    из BK-set дельт?

Любой ответ годится — план B (локальный пересчёт в relayer) у нас
готов. Просто нужно «да/нет», чтобы окончательно зафиксировать формат
public inputs для Circuit 3.


Q3. Полный тест-вектор Poseidon для BK set

У нас есть наблюдаемое значение commitment для лайтнет-стенда:

  0x11e20085fcc3d8d494ba4037e884a2b55909498ff27d4595949a9674f52dd495
  (для 5-signer set из ./bk_set.json)

Но нет точной кодировки входа, по которой оно получено. Хотелось бы
один (или лучше несколько) полностью развёрнутый сэмпл:

  — BK set отсортированный по signer_index;
  — паддинг до 300 записей;
  — развёрнутый в 1800 Fr-инпутов (по 6 на запись:
    [index, limb0, limb1, limb2, limb3, limb4]);
  — итоговый 32-байтовый Poseidon-выход.

Нужно, чтобы у нас в bridge-snark-utils появился независимый
Poseidon, который мы сможем сверить байт-в-байт, не делая
runtime-зависимость на твой крейт как на оракул. Если у тебя уже лежит
такой JSON в test-fixtures — просто покажи путь, нам распакуем.

Идеально — три вектора: N=1 (один реальный signer + 299 паддинг), N=10
и N=300 (без паддинга).
