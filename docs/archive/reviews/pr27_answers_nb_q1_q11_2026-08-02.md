## PR-27-A — `applyBkSetUpdate` leaf byte order is inverted (blocking)

`4f41bfa` computes the leaf-pair hash as

```solidity
bytes32 h23 = sha256(abi.encodePacked(oldCommitmentL2, newCommitmentL3));
```

`abi.encodePacked(uint256)` serialises **big-endian**. The AN side builds L2/L3
from the Poseidon commitments' canonical **little-endian** `Fr` repr —
`crates/an-bridge-prover/bridge-prover-lib/src/block_id_tree.rs:30-31`:

```
//! - L2 = `Poseidon(old_bk_set_hash)` (32 bytes LE) — zero if no BK-set change
//! - L3 = `Poseidon(new_bk_set_hash)` (32 bytes LE) — zero if no BK-set change
```

So `sha256(BE(L2) ‖ BE(L3)) ≠ sha256(LE(L2) ‖ LE(L3))` and
`BkUpdateMerkleMismatch` fires on every real `bkupd_*.json` witness.

The test does not catch it because `_merkleWitness` derives the expected root
with the same big-endian fold, and says so in its own comment:

```solidity
///      Arbitrary sibling literals — the test only checks that the
///      contract reconstructs the same root the helper does.
```

That is self-consistency, not cross-language binding.

**Fix (already on PR #20, branch `pruvendo/deposit-circuit-soundness-fixes`,
commits `6bef5d1` + `d7c87d7`):** the same depth-4 fold plus a `_frToLeBytes`
helper, and a Foundry test pinned to a vector computed independently by
`block_id_tree.rs` rather than by the contract itself.

```solidity
bytes32 h23 =
    sha256(abi.encodePacked(_frToLeBytes(oldCommitmentL2), _frToLeBytes(newCommitmentL3)));
bytes32 h0_3 = sha256(abi.encodePacked(siblingH01, h23));
bytes32 h0_7 = sha256(abi.encodePacked(h0_3, siblingH4_7));
bytes32 root = sha256(abi.encodePacked(h0_7, siblingH8_15));
```

We landed the migration independently on the same day, so the two PRs collide
on this function. Everything else about your version matches (3-sibling
signature, 4-round fold, param naming, the `sol!` binding in
`bridge-relayer-daemon/src/bridge.rs`) — only the leaf serialisation differs.
On merge, **keep the `_frToLeBytes` variant and the pinned vector test**;
otherwise take PR #20's `applyBkSetUpdate` wholesale and drop `4f41bfa`'s
contract hunk.

## NB-Q10 — Hermez SRS provenance of the committed `verifiers/*.bin`

**Short answer: no. I cannot confirm Hermez, because it was not Hermez.** The
committed `.bin` were generated against the **Acki Nacki chain ceremony**
(`s_g2` head `c6028acf…`). Your instinct that a 1-byte drift is "inconsistent
with SRS drift" is the one step that does not hold, and it is what let the
audit line look clean.

**Why the drift is small.** An EVM verifier is succinct: the SRS enters it
*only* through the four G2 limbs of `s_g2` used in the final pairing. The g1
powers never appear in bytecode. So switching ceremonies moves exactly 4
PUSH32 constants — tens of bytes of *content*, and normally **zero** bytes of
*size*.

**Direct evidence.** Taking the committed Jul-15 `PrimaryAggregatorVerifier.bin`
(21493 B), converting the `s_g2` of each candidate SRS out of Montgomery form
and searching the bytecode for the standard-form limbs:

| SRS | file | `s_g2` head | limbs found in committed `.bin` |
|---|---|---|---|
| AN chain ceremony | `crates/bridge-evm-aggregator/params/kzg_bn254_21.srs` | `c6028acf4420…` | **3 / 4** (x₀, x₁ plain; y₀ negated) |
| Hermez PPoT | `crates/bridge-prover-orchestrator/params/kzg_bn254_21.srs` | `928fafb3d0cc…` | 0 / 4 |

The G2 *generator* (identical in both files) is present 4/4 in both binaries,
which confirms the extraction method.

**And the missing fourth limb is exactly your 1-byte drift.** The negated y₁
limb of the chain `s_g2` is

```
00ae44489d41a0d179e2dfdc03bddd883b7109f8b6ae316a59e815c1a6b35304
```

— leading byte `0x00`. solc emits the minimal push width, so it is encoded as
**PUSH31** at offset 21320 (opcode `0x7e` verified in place), 31 bytes instead
of 32. Hermez's corresponding limb is full-width, hence PUSH32. Push-width
histogram across the two binaries:

```
PUSH31: 2 -> 1   (-1)
PUSH32: 134 -> 135  (+1)      net +1 byte:  21493 -> 21494
```

So the drift is not cosmetic. **It is the ceremony.**

**Corroborating timeline.** `PrimaryAggregatorVerifier.bin` has local mtime
**Jun 23 04:06** (C4: Jul 7); the aggregator's own
`params/kzg_bn254_{20,21,22}.srs` are dated Jun 18–22 and all fingerprint as
chain ceremony. The Hermez migration landed later, in #10 / `903efff` +
`2d8c980` on **Jul 14–15**, and covered deposit + Circuit 1B fixtures — the
aggregator `.bin` were carried into #11 unregenerated. That is the gap; it is
the same gap your `c07719a` ("Close remaining Hermez SRS gaps") is closing.

**Answers as asked.**

1. **No.** K=21 outer SRS at generation time was the AN chain ceremony, not
   `powersOfTau28_hez_final_21.ptau`.
2. **Not** a `gen_srs` toxic-waste fallback either — that part of your audit is
   clean. It was a real file with a real multi-party ceremony behind it
   (`zk-powers-of-tau-ceremony-contracts`), just the wrong one for the ETH
   side. So this is a **policy and interop** break, not "tau is known to a
   local process". No emergency, but not filable as clean.
3. Fully explained above: PUSH31→PUSH32 on one negated `s_g2` y-limb. Nothing
   to pin in `AggregationConfigParams` or solc; both binaries carry the same
   `…64736f6c6343000813 0033` tail (solc 0.8.19) and identical opcode structure
   for the first 10 414 of 10 420 instructions, diverging only 43 bytes from
   the end — inside the CBOR metadata trailer.

**Consequences, and what I have already done.**

- `af66323` is therefore not just a "16-leaf refresh" — it is also the ceremony
  cutover for all four verifiers. Worth saying so in the commit/PR text,
  because it changes the deployment story.

  (chain inner + chain outer) which is why the Sepolia `verifyBlock` /
  `withdrawByProof` runs succeeded. Once the prover is Hermez-only
  (`assert_hermez_ceremony` in `keys/common.rs`), the deployed June verifiers
  will reject every new proof. The cutover has to be atomic: **redeploy all
  four verifier contracts + a fresh bridge, and re-bootstrap anchors.** An
  in-place prover switch against the currently deployed verifiers will simply
  halt the bridge.

  `crates/bridge-evm-aggregator/params/kzg_bn254_{9,20,21,22}.srs` were all
  chain-ceremony files sitting exactly where `gen_srs` looks. Renamed to
  `QUARANTINE_an_chain_ceremony_*.bak` so no regeneration can silently pick
  them up again. Your `srs_guard::assert_hermez_ceremony` would now catch this
  anyway — it is the right check and it should stay mandatory (no bypass env
  var).
- Suggested hardening on top: have `aggregate-proof` write the `s_g2` head and
  the SRS file path into a `.provenance.json` next to each emitted `.bin`, and
  add a CI job that re-derives it. Then this question is answerable by reading
  a file instead of by disassembling bytecode.

## NB-Q11 — Circuit 4 calldata on smartphone

1. **Role-split is accepted; mobile-only outer aggregation is not a
   requirement.** Your numbers match ours and the constraint is hard: there is
   no maintained `solc` for iOS/Android ARM64, and ~6–10 GB peak at K=21 is
   past iOS jetsam regardless. Phone emits the inner Circuit-4 Snark; server

   `VerifierUniversality::Full` the outer aggregation is public-coin over the
   inner Snark bytes with no secret witness, so outsourcing it leaks nothing
   and reduces to inner-proof soundness. Topology: start with a **single
   bridge-operated aggregation service**, but design the wire format so the
   aggregator is **user-selectable from day one** — the request is
   `(inner snark, public instances)` and the response is calldata the user
   verifies locally by `eth_call`-simulating `withdrawByProof` before signing.
   That keeps the centralised relay a *liveness* dependency only, and makes
   BYO-aggregator a config change rather than a redesign. Withdrawal
   censorship-resistance then reduces to "can the user run the aggregator
   themselves", which is true on any laptop.
3. Not needed given (1). Lock in role-split now. Folding (Nova/SuperNova) or
   Metal/Vulkan MSM is a partner-scope research item, not on the critical path.
4. **Strongly agree — and stronger than you propose.** The
   `gen_evm_verifier_shplonk` self-check at `aggregate_proof.rs:84-104` should
   default **off everywhere**, and be **on only in CI**. It is a drift audit
