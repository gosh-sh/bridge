# Review — `gosh-sh/bridge` PR #20 (pause removal + deposit `chainId` PI + multi-L2)

**Reviewed:** 2026-07-29 against head `9ed84e0` (77 files, +6860/−18630, base `main`).
**Scope of this pass:** the multi-L2 deposit path (`deposit-prover` header/receipt
handling, `supported_chains`), the 12-PI plumbing through `deposit-relayer-daemon`,
the pause removal in `AckiNackiBridge.sol`, and the fixtures shipped with the PR.

**Verdict:** the 12-PI plumbing is consistent end-to-end and the pause removal is
mechanically clean, but the **multi-L2 claim does not hold on any of the six L2s
as written**, and the shipped fixtures hide it because nothing checks the block
header against the block hash. R1–R3 must land (and force one more VK rotation)
**before** the shellnet redeploy; R4–R6 are operational cliffs; R7–R9 are polish.

---

## R1 — Header table stops at Cancun (20 fields); 5 of 7 allowlisted chains are Prague (21 fields) today — **High, liveness**

`circuit_v2.rs` pins the header layout at axiom-eth's 20-slot Cancun/Ecotone table
and says so explicitly:

```66:66:deposit-prover/src/circuit_v2.rs
pub const MAX_BLOCK_HEADER_BYTES: usize = 668;
```

```70:91:deposit-prover/src/circuit_v2.rs
pub const BLOCK_HEADER_MAX_FIELD_LENS: [usize; 20] = [
    32,  // 0: parentHash
    // ...
    32,  // 19: parentBeaconBlockRoot (post-Cancun / Ecotone)
];
```

with the comment *"No Prague `requestsHash` — axiom's table stops at the Cancun
20th slot."* `encode_block_header` mirrors this: it appends at most
`parentBeaconBlockRoot` and has no `requestsHash` branch.

Live survey of `eth_getBlockByNumber("latest")` on 2026-07-29:

| chain | `requestsHash` | header fields | provable today |
|---|---|---|---|
| Arbitrum One | — (also no `withdrawalsRoot`) | 16 | ✗ (see R3) |
| Base | present | 21 | ✗ |
| Mantle | present | 21 | ✗ |
| World Chain | present | 21 | ✗ |
| OP Mainnet | present | 21 | ✗ |
| Blast | — | 20 | ✓ |
| Sepolia (shellnet target) | present | 21 | ✗ |

The PR's own OP-Stack fixture proves the point. `fixtures/op_ecotone_header_sample.json`
is OP Mainnet block `0x936a48b`, whose real hash is
`0x2c524d0047f1920b782f606f730f8f05998a5cc3e2ed3f6514e3cd606992a604`:

- encoding its 20 fields (what `encode_block_header` does) → keccak
  `0x94e3316f0c4ac8dd510894016a2d0f7d13730967b7af32c69aeca017634e0d37` — wrong;
- appending `requestsHash = 0xe3b0c442…7852b855` (21 fields) → keccak
  `0x2c524d00…6992a604` — exact match, 635 bytes.

So the fixture meant to validate OP-Stack support actually demonstrates that the
encoder cannot reproduce OP Mainnet's header hash.

**Good news on sizing:** 21 fields with a 32-byte `extraData` lands at ≈651 B, so
`MAX_BLOCK_HEADER_BYTES = 668` does **not** need to move. Only
`BLOCK_HEADER_MAX_FIELD_LENS` grows by one 32-byte slot (and
`decompose_rlp_array_phase0` gets a 21-entry vector), which still changes the
constraint system → **one more VK rotation**. Land R1+R3 together so we rotate
once, not twice, and do it before the shellnet `USDCBridge` redeploy.

## R2 — Nothing asserts `keccak(header_rlp) == block.hash`, and all 10 shipped fixtures violate it — **High, correctness of the `blockHash` PI**

`mpt.rs` encodes the header and stores it without ever checking it against the
hash the RPC returned:

```106:113:deposit-prover/src/mpt.rs
    let block_header_rlp = crate::rlp_utils::encode_block_header(&block)?;

    Ok(ReceiptProof {
        receipt_rlp,
        proof_nodes: proof,
        receipt_root: receipts_root,
        block_header_rlp,
    })
```

Consequence, measured on the committed fixtures: every
`deposit_10proofs/proof_0*/input.json` and `chain_binding_sepolia_dep0/input.json`
carries a **17-field** header — no Cancun blob fields at all — even though they
come from real Sepolia blocks (`#11025192`, `#11115635`, `#11196834`). For
`#11025192` the fixture's `parentHash` (`ec3004c8…f480bf`), `extraData`
(`"Powered by bloXroute"`) and `timestamp` (1781040996) match the live block
exactly, yet:

- fixture header keccak = `0xd57f38a0d818114f84182f810a1ae493dd0a18097a4d52649b99aff43a777b45`
- real Sepolia block hash = `0x34fbf8176bf9d318a360f2106568446a81ba2a460e9f4a32b9b263baa25d5436`

So the `blockHash` public input in every fixture — and in any live proof this path
has produced — is the hash of a truncated, non-canonical header. The deposit event
itself is still genuine (`receiptsRoot` is real, and after #26 it is bound to the
root the MPT chip verified), so this is not a new mint hole; but it makes the V1
"canonical block hash" cross-check in `docs/verifying_eth_proof_on_an.md` §1
permanently unsatisfiable, i.e. it removes the only documented defense against
phantom-block proofs and forecloses ever adding a header oracle on the AN side.

The existing unit test deliberately declines the assertion that would have caught
this:

```483:489:deposit-prover/src/rlp_utils.rs
    /// Live OP Stack Ecotone header sample: encoding must include Cancun
    /// blob fields and stay under [`crate::circuit_v2::MAX_BLOCK_HEADER_BYTES`].
    /// Full `keccak == block.hash` is covered by axiom-eth's provider tests
    /// against live Base/OP (`get_block_rlp`); reconstructing a `Block` from a
    /// truncated JSON snapshot is fragile (Bloom / type widths), so we only
    /// assert structural properties here.
```

The snapshot is not in fact too truncated — I reproduced the hash by hand from
exactly those fields. Asks:

1. `ensure!(keccak256(&block_header_rlp) == block.hash, …)` in both the receipt and
   tx proof builders (two lines, converts a silent semantic break into a loud one).
2. Promote the OP sample test to a real `keccak == hash` assertion (add
   `requestsHash` to the sample once R1 lands).
3. Regenerate `deposit_10proofs` *witnesses* from live blocks, not just re-prove the
   stored `input.json` — `export_deposit_proof_set` re-proves existing witnesses, which
   is why the #26 rotation carried the stale 17-field headers forward.

## R3 — Arbitrum One's `gasLimit` needs 7 bytes; the table allows 4 — **Medium, liveness**

Arbitrum One is in `SUPPORTED_DEPOSIT_CHAIN_IDS`, but its header `gasLimit` is
`0x4000000000000` (2^50, 7 bytes) against `BLOCK_HEADER_MAX_FIELD_LENS[9] = 4`, so
`decompose_rlp_array` cannot accept an Arbitrum header. (Its 16-field shape — no
`withdrawalsRoot`, no Cancun fields — is fine, the variable-length path handles
that; `number` at 489,326,390 still fits in 4 bytes.) Bump that slot to 8 and fold
it into the R1 rotation.

## R4 — `transaction_type == 2` is a hard constraint; a non-1559 deposit is unprovable and unrefundable — **Medium, liveness / stranded funds**

```344:346:deposit-prover/src/circuit_v2.rs
        let eip1559 = ctx.load_constant(Fr::from(EIP1559_TX_TYPE));
        ctx.constrain_equal(&tx_witness.transaction_type, &eip1559);
        println!("   ✓ Constrained tx type == EIP-1559 (0x02)");
```

Sound as a binding (RLP field 0 is only `chainId` for type-2), but the EVM
`deposit()` cannot see its own tx type, so a user who sends the deposit as a
legacy (0x00), 2930, 4844 or 7702 transaction gets a successful on-chain deposit
that can never be finalized — and the refund-style `withdraw()` was retired in
Phase 4.3, so there is no recovery path. At minimum: pre-flight the tx type in the
relayer and fail with a distinct terminal error before spending ~46 s of proving,
and document the constraint in `deposit()`'s NatSpec + the user guide. Ideally
extend the circuit to type-0/1 (chainId from `v`, or from the header/consensus).

## R5 — the production `daemon` path skips the chain allowlist — **Medium, ops**

`ensure_supported_rpc_chain` (allowlist + optional `--expect-chain-id`) is wired
into `watch` and `prove-one` only. `run_daemon` reads the chain id raw:

```687:692:crates/deposit-relayer-daemon/src/bin/deposit-relayer.rs
    let provider = ProviderBuilder::new().connect_http(rpc_url.parse()?);
    let chain_id = provider
        .get_chain_id()
        .await
        .map_err(|e| anyhow::anyhow!("get_chain_id failed: {e}"))?;
    let deployment = DeploymentIdentity::new(chain_id, bridge_address, prover_cfg.dapp_id.clone());
```

and `Cmd::Daemon` has no `--expect-chain-id`. Point the daemon at mainnet or a
local anvil and it will prove and submit deposits the AN allowlist is guaranteed to
reject. One-line call + the flag, for parity with the one-shot commands.

## R6 — the chain allowlist is duplicated across two cargo trees with nothing pinning them — **Medium, drift**

`deposit-prover/src/supported_chains.rs` and
`crates/deposit-relayer-daemon/src/supported_chains.rs` hold two independent
copies of the same seven constants; each test asserts `len() == 7` on its own copy,
so a chain added on one side and not the other is invisible. This is the exact
shape of the `HISTORY_PROOF_WINDOW_SIZE` duplicate-constant drift that burned
several full E2E runs in May (AGENTS.md § "Partner Prover Bug Found"). The relayer
deliberately doesn't depend on `deposit-prover` (halo2 build cost), so the cheap fix
is a tiny leaf crate (`crates/deposit-chain-ids`) path-dep'd from both trees.

## R7 — `--chain-id` on the prover examples is now decorative — **Low**

The circuit explicitly ignores it:

```147:147:deposit-prover/src/circuit_v2.rs
        let _ = config.expected_chain_id; // demoted: not a VK / soundness input
```

so the flag's only remaining effect is `require_supported_deposit_chain`. Because
it defaults to Sepolia (which is in the allowlist), proving a Base or OP deposit
without passing the flag sails through a check that reads like it validates
something. Either drop the flag or make it assert against the chainId actually
extracted from the tx.

## R8 — pause removal has no stated rationale and no replacement lever — **Low / process**

`AckiNackiBridge` is not upgradeable, so after this PR there is no way to stop
payouts if a Circuit-4 or `verifyBlock` soundness bug is found while ETH and aWETH
are custodied. The commit message (`c0da8a3`) just says "Drop global pause". If
this is a deliberate trust-minimisation call, put that in the PR body along with
what replaces it (per-epoch payout cap, timelocked verifier swap, or an explicit
"no lever, accepted risk" sign-off).

## R9 — PR body fixture table is stale — **Nit**

It still lists `006cca5d…191dec05`; #26 rotated the blob to
`3e2a2db2…bf0d049c` (same 12-PI layout, 5006 B). Either update the table or point
it at `docs/deposit_max_key_byte_len.md`, which is now the single source of truth
for the fixture rotation.

## AN-side counterpart (out of PR #20's tree)

`USDCBridge_12pi_chainid_allowlist.patch` closes the review's Section 2/3 asks:
`_expectedBridgeFr[chainId] == contractAddr` (fail-closed, so an unknown chain and
an empty-RLP `chainId == 0` both reject) plus a `dappId == _expectedAnDappId`
require. Two notes for the runbook rather than the code:

- the allowlist is intentionally not threaded through `onCodeUpgrade`, so **every
  deposit rejects after a code upgrade until the owner re-seeds
  `setExpectedBridge` / `setExpectedAnDappId`** — that needs to be a checklist step,
  not a comment;
- `_parsePublicInputs` keeps `require(fr[2] <= uint64::max)` while the circuit's new
  range check allows `< 2^128`. Fine as a tighter bound, but the relayer should
  mirror it so an oversized deposit fails before we spend a proof on it.
