# Halo2 on-chain verification — gnark wrapper vs. Yul verifier

**Status:** background note for R15 decision-making (Path B chosen for production). Updated 2026-07: all four circuits use R15 SHPLONK `.bin` verifiers on Ethereum.

---

## Two paths to verify a Halo2 proof on Ethereum

### Path A — gnark Groth16 wrapper (today's production stack, **stubbed**)

```
Halo2 proof  →  gnark wrapper circuit (Define())  →  Groth16 proof  →  Solidity Groth16 verifier
(off-chain)     (off-chain, in gnark Go)             (~256 B)          (~250k gas)
```

The wrapper circuit's `Define()` is supposed to encode the Halo2 SHPLONK verifier algorithm as R1CS constraints; producing a Groth16 proof of that circuit attests *"a valid Halo2 proof exists for these PIs"*. The on-chain Solidity verifier itself is dumb — one BN254 pairing check, identical to any Groth16 verifier.

**Today on this repo:** all four `crates/bridge-prover-orchestrator/gnark-wrappers/circuit-{1a,1b,2,4}/circuit.go` files have **identity-stub `Define()` bodies** (`api.AssertIsEqual(PI[i], PI[i])`). Byte-for-byte identical across every open branch on `gosh-sh/bridge-EVM` (verified 2026-06-18). The on-chain Groth16 proof attests to *nothing about the Halo2 layer* — the wrapper PK holder can mint a valid Groth16 proof for any PI tuple.

### Path B — Yul Halo2 verifier (R15 target, **spike-only**)

```
Halo2 proof  →  AggregationCircuit (snark-verifier-sdk)  →  Halo2 SHPLONK proof  →  Yul EVM verifier
(inner)         (off-chain wrap, K≈21)                      (~24 KB)                (~13 KB, ~300–500k gas)
```

`snark-verifier-sdk::gen_evm_verifier_shplonk` is a code generator: given a Halo2 verifying key, it emits a **Yul program** that directly implements the Halo2 SHPLONK verifier (Fiat-Shamir reconstruction, MSM, KZG opening checks, final BN254 pairing via EIP-1108 precompile at `0x08`). `solc` compiles it to deployable bytecode. The contract has no functions — just a `fallback()` that decodes `instances ‖ proof` and reverts on a bad pairing.

The off-chain `AggregationCircuit` wrap exists because verifying a raw Halo2 proof directly would exceed EIP-170's 24 576-byte runtime-code cap; the aggregator defers the final pairing into 12 KZG accumulator limbs surfaced as outer-proof instances, keeping the Yul verifier at fixed ~13 KB regardless of inner-circuit complexity.

**Today on this repo:** `crates/bridge-evm-aggregator/` is a standalone-workspace **feasibility spike**. M2 closed 2026-05-27 with a trivial `multiply.rs` inner (proving `a*b == c`); M5 instance-exposure de-risked 2026-05-29. The spike's Yul output `target/spike/AggregatorVerifierSpike.{sol,bin}` is `.gitignore`d and **not wired into any production contract**.

## Cost / risk comparison

| | Path A (gnark wrapper) | Path B (Yul verifier) |
|---|---|---|
| On-chain code size | ~3 KB | ~13 KB (fits EIP-170 with margin) |
| Per-verify gas | ~250k | ~300–500k |
| Calldata size | ~256 B (Groth16 proof) | ~24 KB (proof + instances) |
| Trusted setup | **Per-circuit Groth16 ceremony** | Reuses existing KZG SRS (Hermez PPoT) |
| Verifier code source | Hand-written | Generated by `snark-verifier-sdk` (audited) |
| Production precedent | None (no public Halo2-in-gnark deploy exists) | **Axiom V2 on Ethereum mainnet since 2024-01-22** |
| Soundness audit surface | New per-circuit | snark-verifier-sdk (Spearbit + Zellic + Trail of Bits) |

## Can a Halo2 verifier be reused from gnark off-the-shelf?

**No.** The cryptographic primitives are there, but the Halo2-specific glue is not.

### What gnark already has (the building blocks)

- `consensys/gnark/std/commitments/kzg` — in-circuit KZG verification on BN254 ✅
- `consensys/gnark/std/algebra/emulated/sw_bn254` — BN254 G1/G2/pairing emulated in BN254 scalar field ✅
- `consensys/gnark/std/recursion/plonk` — **vanilla** PLONK-KZG verifier in-circuit ✅ (but **gnark-native PLONK only**, not Halo2)
- `consensys/gnark/std/recursion/groth16` — Groth16-of-Groth16 ✅
- Poseidon over BN254 in `gnark-crypto` ✅

### What gnark does NOT have

`std/recursion/plonk` is vanilla PLONK-KZG only. It does **not** support:
1. Halo2's transcript layout (absorption order + challenge-squeeze cadence differs from gnark-native PLONK)
2. Halo2 custom gates — every circuit's polynomial-identity evaluator is bespoke (Circuit 1A's BLS gates ≠ Circuit 2's Merkle gates ≠ Circuit 4's nullifier gates)
3. Halo2 lookup arguments (`(z, h, h')` encoding differs from gnark's lookups)
4. SHPLONK multi-point opening (gnark's PLONK does single-point KZG; SHPLONK aggregates many opening points with `v^i` linear combinations)
5. Halo2's multi-column permutation argument

### Survey: who has done Halo2-in-gnark in production?

**Nobody.** Surveyed 2026-06-18:

| Project | What they did | Path |
|---|---|---|
| **Axiom** (mainnet 2024-01-22) | Halo2 + KZG-BN254 + snark-verifier-sdk → Yul | **Path B** (Yul) |
| **Scroll** (zkEVM) | Halo2 + KZG-BN254 → Solidity verifier | Path B (Yul); `halo2-snark-aggregator` archived 2023-07 |
| **Linea (Consensys)** | Vortex → Arcane → PLONK compression, all gnark-native | Avoids the problem — no external Halo2 in the path |
| **PSE** (`halo2-solidity-verifier`) | Halo2 → Solidity/Yul code gen | Path B (Yul) |
| **DelphinusLab** (`halo2aggregator-s`) | Rust aggregator → Solidity | Path B (Yul) |
| **Succinct Labs** (`gnark-plonky2-verifier`) | **Plonky2** (not Halo2) → gnark | Closest analog; multi-engineer multi-month effort |
| **Quark Layer** | Halo2-in-gnark "**planned**" | Not done |

The closest analog to Halo2-in-gnark is Succinct Labs' Plonky2-in-gnark — a *different* proof system, similar shape (polynomial IOP + opening + transcript), and the effort was substantial. No team has done the Halo2 equivalent.

### Effort estimate if Path A is nonetheless taken

Assuming an engineer fluent in both Halo2 internals and gnark, building on the off-the-shelf primitives:

| Step | Effort | Notes |
|---|---|---|
| Witness struct mapping | 1–2 days | mechanical |
| Halo2 Poseidon-FS transcript matching byte-exactly | 5–10 days | gnark Poseidon exists, but Halo2's absorption order is not reusable |
| Polynomial identity eval at challenge `x` (per-circuit gates + perm + lookup) | **2–4 weeks per circuit** | the bulk of the work; cannot be shared across circuits |
| SHPLONK batching (`v^i / (x-z_i)` linear combinations) | 3–5 days | builds on `std/commitments/kzg` |
| Final BN254 emulated pairing | 1–2 days | `sw_bn254` library call |
| Negative-test / soundness fuzzing | 2–3 weeks | silent-acceptance is the failure mode |
| Trusted setup ceremony | weeks of governance | per circuit (or one batched) |

**Circuit 1A alone: ~6–10 weeks** on top of ceremony. **All four circuits: ~3–5 months** (only the polynomial-identity step is per-circuit; the framework reuses). Plus ramp-up if the engineer isn't already fluent in both stacks.

**No production precedent exists.** Soundness risk is the soundness risk of a fresh re-implementation of a verifier that has never been built before in gnark.

## Why Axiom matters as precedent

Axiom is the team that *built* halo2-lib and `snark-verifier-sdk`. They use Halo2 more heavily than anyone in production. **They chose Path B (Yul) and never considered gnark.** Their V2 stack:

| Component | Axiom V2 | `bridge-evm-aggregator` (R15 target) |
|---|---|---|
| Inner proof system | Halo2 + KZG-BN254 (PSE fork) | Halo2 + KZG-BN254 (gosh fork of PSE) |
| Aggregation | `snark-verifier-sdk::AggregationCircuit` | Same |
| Yul code-gen | `gen_evm_verifier_shplonk` | Same (gosh-sh/snark-verifier pinned at `ccdb510`) |
| On-chain contract | Yul verifier behind UUPS + TimelockController (1-week delay) | Will become `BridgeWithdrawalAggregatorVerifier.sol` |
| Transcript | **Keccak** (cheap on-chain via `SHA3` opcode) | **Poseidon** (M3 in orchestrator) |
| Audited by | Spearbit, Zellic, Trail of Bits | (TBD) |

The R15 roadmap is following Axiom's playbook precisely. The one substantive divergence is **transcript choice**: Axiom uses Keccak (cheaper for the on-chain Fiat-Shamir reconstruction); R15 picks Poseidon (cheaper inside the inner Halo2 prover). For Circuit 4 this is fine; for Circuits 1A/1B/2 (called per-block) the gas trade-off is worth re-evaluating — Axiom didn't pick Keccak by accident.

## Recommendation

For the four-circuit problem (1A/1B/2/4):

- **Path B (Yul) is the realistic option** — production-validated by Axiom, zero new cryptography work, soundness rides on snark-verifier-sdk's audit history. Effort is days–weeks per circuit beyond what the M2 spike already proved.
- **Path A (gnark) is a research project** — no public precedent, 3–5 months at minimum, fresh soundness audit surface, extra trusted-setup ceremony. Only worth considering if Path B is gas-blocked for per-block circuits (1A/1B).
- **Option C — explicit relayer-trust for 1A/1B/2** with documented threat model and on-chain compensating control (multisig, challenge window) — is the third honest option, distinct from both A and B.

`bridge_evm_review_questions.md` Q2 frames these as Options A/B/C; this note is the technical backing.
